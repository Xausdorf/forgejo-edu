## 1. Первый запуск и настройка ролей

### Регистрация

1. Откройте `http://localhost:3000` (или адрес вашего сервера).
2. Нажмите **Register** и создайте аккаунт.
3. **Первый зарегистрированный пользователь** автоматически становится администратором Forgejo.

### Вход в образовательный модуль

После входа в систему в верхней навигации появится ссылка **Education**. Нажмите на неё — вы попадёте на `/edu/dashboard`, который автоматически перенаправит вас на нужную панель в зависимости от вашей роли:

| Роль | Перенаправление |
|------|----------------|
| **teacher** | `/edu/teacher/assignments` — список заданий |
| **student** | `/edu/student/assignments` — список доступных заданий |
| **admin** | `/edu/admin` — панель управления ролями |
| Роль не назначена | Страница со ссылкой на панель администратора |

> **Важно:** Чтобы использовать образовательный модуль, администратор должен сначала назначить роли пользователям через панель администратора (`/edu/admin`).

## 2. Панель преподавателя

### 2.1. Курсы

#### Создание курса

1. Перейдите на вкладку **Courses** (верхняя навигация на странице преподавателя).
2. Нажмите зелёную кнопку **New Course** (справа вверху).
3. Заполните форму:
   - **Name** — название курса (обязательно)
   - **Description** — описание
   - **Start Date** — дата начала (необязательно)
   - **End Date** — дата окончания (необязательно)
4. Нажмите **Create Course**.

#### Просмотр курса

На странице курса (`/edu/teacher/courses/{id}`) отображаются три секции:

- **Информация о курсе** — описание, даты, статус (Active / Ended).
- **Assignments** — список заданий курса с количеством submissions. Кнопка **New Assignment** создаёт задание, привязанное к этому курсу.
- **Participants** — таблица участников с ролями.

#### Редактирование и удаление курса

- Кнопка **Edit** (карандаш) — редактирование названия, описания и дат.
- Кнопка **Delete** (красная) — удаление курса (с подтверждением).

#### Управление участниками

На странице курса, в секции **Participants**:

1. Введите **Username** пользователя Forgejo.
2. Выберите роль: **Student** или **Teacher**.
3. Нажмите **Add**.

Для удаления участника нажмите красную кнопку **Remove** напротив его имени.

### 2.2. Задания

#### Создание задания

1. Перейдите на `/edu/teacher/assignments/new` или нажмите «Новое задание» в списке курсов.
2. Заполните форму:
   - **Курс** — выберите курс (обязательно). У курса должен быть установлен `tasks-master` репозиторий.
   - **Task name** — короткий идентификатор папки задания, регулярка `^[a-z0-9_-]+$`. Например, `multiplication`, `linked-list`, `hw01`.
   - **Title** — человеко-читаемое название (≤255 символов).
   - **Allowed files glob** — авторитетный список путей, которые студент имеет право менять. Например, `tasks/multiplication/multiplication.cpp`. Сервер будет блокировать сабмиты с изменениями вне glob-а.
   - **Deadline** — дедлайн.
3. Перед отправкой формы убедитесь, что в `tasks-master` уже создана и запушена ветка `submits/<task_name>` с подготовленным шаблоном задания. Сервер проверит это при сохранении — если ветки нет, форма не сохранится.
4. После создания нажмите «Распределить» (`Distribute`) на странице задания, чтобы запушить ветку `submits/<task_name>` во все студенческие форки и создать пустые сабмиты в статусе `pending`.

#### Редактирование задания

На странице submissions задания нажмите **Edit Assignment** — можно изменить название, описание и дедлайн.

#### Удаление задания

На странице submissions нажмите красную кнопку **Delete** (с подтверждением). Удаляются задание и все связанные submissions.

### 2.3. Проверка работ

#### Таблица submissions

Перейдите на страницу задания: **Assignments** → нажмите **Submissions** на карточке задания.

Таблица показывает:

| Колонка | Описание |
|---------|----------|
| **Student** | Имя студента |
| **Status** | `started` (серый), `submitted` (синий), `passed` (зелёный), `failed` (красный), `graded` (фиолетовый) |
| **CI Score** | Процент прохождения тестов + короткий хеш коммита |
| **Grade** | Оценка `X/100` или «Not graded» |
| **Repo** | Ссылка на репозиторий студента |
| **Updated** | Дата последнего обновления |
| **Detail** | Кнопка перехода к детальной странице |

#### Детальная страница submission

На странице `/edu/teacher/assignments/{id}/submissions/{subID}`:

- **Информация** — задание, студент, статус, ссылка на репозиторий.
- **CI/CD Test Results** — таблица всех прогонов CI: номер, коммит, оценка (%), детали, дата.
- **Grading** — форма выставления оценки:
  1. Введите оценку от **0 до 100**.
  2. Добавьте **комментарий** (необязательно).
  3. Нажмите **Save Grade**.

После сохранения оценки статус submission изменится на `graded` (фиолетовый).

### 2.4. Автоматическое оценивание через CI

CI-workflow живёт в `tasks-master/.forgejo/workflows/grade.yml`. Он запускается на push любой ветки `submits/**` (то есть после студенческого пуша в свой fork по этой же ветке) и обычно состоит из трёх шагов:

1. **Constraint check (по конвенции)** — `git diff --name-only main...HEAD | grep -v "^tasks/<task>/"`; если что-то снаружи папки задания — `exit 1`.
2. **Lint / Build / Test** — преподаватель пишет под свой стек (clang-format / cmake / pytest / npm test).
3. **Grade marker** — `echo "::edu-grade::100"` (или меньше — например, отношение пройденных тестов к общему числу).

Authoritative constraint check проводится сервером (по `Assignment.AllowedFilesGlob`), даже если CI сделал свой более слабый — на это полагаться можно.

#### Ручная коррекция оценки

После того как CI отработал, статус сабмита меняется на `done` и в студенческом fork-е появляется PR `submits/<task>` → `main`. TA / преподаватель открывает submission через `/edu/teacher/assignments/{id}/submissions/{subID}`:
- видит diff и комментарии PR прямо на edu-странице;
- может оставить комментарий («Approve», «Reject», «Доработать», и т.д.);
- нажимает **Approve** — фиксирует оценку (по умолчанию в форму уже подставлена CI auto-grade) и комментарий, статус становится `approved`, `ManualGrade=true` (последующие CI-прогоны больше не перезапишут оценку);
- нажимает **Merge** — fast-forward / 3-way-merge ветки в `main` от имени `eduadmin`, статус `merged`.

#### Сброс на автоматическую оценку

Кнопка «Reset Approval» возвращает статус из `approved` в `done` и сбрасывает `ManualGrade` в `false`. После этого следующий CI-прогон может снова обновить grade автоматически.

### 2.5. Init forks (инициализация студенческих форков)

После того как CSV-импорт или ручное зачисление студентов завершено, преподаватель один раз нажимает **Init forks** на странице курса. Сервер:
- Создаёт fork `tasks-master` под именем `<username>-tasks` для каждого зачисленного студента в той же org-е, что и `tasks-master`.
- Настраивает на `main` форка branch protection (никто не пушит напрямую; merge только через edu-UI под `eduadmin`).
- Добавляет студента как Write-collaborator на свой fork (он не имеет доступа к чужим форкам).
- Сохраняет `Enrollment.StudentForkRepoID`.

Операция асинхронная: страница показывает прогресс-бар, обновляющийся через JSON-эндпоинт `/init-forks-status`. Можно безопасно перезапускать — повторный init-forks пропустит уже инициализированных.

### 2.6. Distribute (раздача задания)

После создания задания преподаватель нажимает **Distribute** на странице задания. Сервер:
- Пушит ветку `submits/<task_name>` из `tasks-master` во все студенческие форки.
- Создаёт `Submission(Status=pending)` на каждого зачисленного студента.

Прогресс — `/distribute-status`. После distribute студент видит задание в `/edu/student/assignments`, может git clone свой fork, переключиться на ветку `submits/<task_name>`, делать коммиты, и пушить — это запустит CI и в конечном счёте создаст PR.

### 2.7. Course sync (синхронизация шаблона в форки)

Если преподаватель что-то поправил в `tasks-master` (например, обновил тесты в существующем задании или добавил новое) и хочет «втянуть» эти изменения во все студенческие форки, он идёт на `/edu/teacher/courses/{id}/sync` и нажимает **Запустить синхронизацию**. Сервер для каждого fork-а:
- Пушит ветку `course-sync` из `main` `tasks-master` в fork.
- Открывает PR `course-sync` → `main`.
- Пробует auto-merge.

Дальше TA смотрит таблицу:
- Зелёные строки (merged) — ничего делать не надо.
- Жёлтые (conflict) — открыть PR, разрешить конфликт вручную, нажать Merge.
- Кнопка **Merge все без конфликтов** мержит скопом всё, что можно.

Фильтр по группе работает на этой же странице (`?group=se241`).

### 2.8. Импорт студентов из CSV

Трёхшаговый процесс импорта студентов в курс.

#### Шаг 1: Загрузка CSV

1. На странице курса нажмите **Import from CSV** (бирюзовая кнопка).
2. Выберите CSV-файл (`.csv` или `.txt`).
3. Настройте параметры:
   - **First row is header** — отметьте, если первая строка содержит заголовки.
   - **Full Name column** — индекс колонки с ФИО (начиная с 0).
   - **Email column** — индекс колонки с email (`-1` = автогенерация).
   - **Group column** — индекс колонки с группой (`-1` = пропустить).
4. Нажмите **Upload and Preview**.

> **Поддерживаемые форматы:** UTF-8 и Windows-1251, разделитель — запятая или точка с запятой (определяется автоматически). BOM-маркер удаляется автоматически.

#### Шаг 2: Предварительный просмотр

На странице preview отображается таблица со всеми строками:

- **Full Name** — ФИО из CSV.
- **Username** — автоматически сгенерированный логин (транслитерация кириллицы по ГОСТ 7.79-2000).
- **Email** — email из CSV или автосгенерированный.
- **Status** — `Pending` (жёлтый), `Exists` (синий — пользователь уже есть).

Можно отредактировать **username** и **email** для каждой строки прямо в таблице (нажмите **Save** после изменений).

#### Шаг 3: Выполнение импорта

1. Выберите роль по умолчанию (**Student** или **Teacher**).
2. Нажмите **Import All** (с подтверждением).

После импорта отображается результат:
- **Total Rows** — всего строк.
- **Created** — создано новых пользователей.
- **Already Existed** — уже существующие.
- **Errors** — ошибки.

Если были созданы новые пользователи, отображается таблица с логинами и **сгенерированными паролями**. Нажмите **Download Credentials CSV**, чтобы сохранить их.

> **Важно:** Пароли показываются только один раз! Обязательно скачайте CSV.

## 3. Панель студента

### Список заданий

`/edu/student/assignments` показывает все сабмиты студента, упорядоченные по дате создания. Колонки:
- **Title** — название задания.
- **Course** — курс.
- **Branch** — `submits/<task_name>` (ссылка на ветку в форке).
- **Status** — pending / running / done / approved / merged / failed.
- **Grade** — текущая оценка (либо CI auto-grade, либо TA-зафиксированная).

Видны только задания из активных курсов (где `EndUnix==0` или ещё не прошёл).

### Детальная страница задания

`/edu/student/assignments/{id}` показывает:
- Метаданные задания (название, курс, дедлайн, allowed files glob).
- Ссылку на свой fork (`<username>-tasks`).
- Ссылку на ветку `submits/<task_name>`.
- Ссылку на CI run (если уже стартовал).
- Ссылку на PR (если notifier его создал).
- Текущий статус и оценку.

### Рабочий процесс студента

1. Преподаватель раздаёт задание (`Distribute`) — у студента появляется запись в `/edu/student/assignments` со статусом `pending`.
2. Студент открывает свой fork (`{org}/<username>-tasks`), переключается на ветку `submits/<task_name>`. Шаблон задания уже там.
3. Студент клонирует fork локально, пишет код в файлах, разрешённых `AllowedFilesGlob`, коммитит, пушит в `submits/<task_name>` своего форка.
4. Forgejo Actions запускает workflow `grade.yml`. Статус сабмита переходит в `running`.
5. После CI-прогона notifier создаёт PR `submits/<task_name>` → `main` (если ещё нет), пишет `TestResult` и оценку, ставит статус `done` (или `failed` при нарушении constraint-check / падении тестов).
6. TA открывает submission через edu-UI, оставляет комментарии, нажимает Approve, потом Merge. Студент видит финальный статус `merged` и зафиксированную оценку.

## 4. Панель администратора

Доступна по адресу `/edu/admin` для пользователей с ролью `admin`.

### Управление ролями

1. Введите **Username** пользователя Forgejo.
2. Выберите роль из выпадающего списка:
   - **student** — доступ к студенческой панели.
   - **teacher** — доступ к панели преподавателя (курсы, задания, проверка).
3. Нажмите **Set Role**.

> **Без назначенной роли** пользователь не сможет пользоваться образовательным модулем — при переходе на `/edu/dashboard` он увидит сообщение с просьбой обратиться к администратору.

## 5. Типичные сценарии

### Сценарий: Полный цикл задания

1. **Преподаватель** создаёт курс с `OrgID` и `TasksMasterRepoID`.
2. Импортирует студентов из CSV (с колонкой Group).
3. Жмёт **Init forks** — для каждого студента создаётся `<username>-tasks` в org-е, с branch protection и collaborator-записью.
4. Коммитит в `tasks-master` папку `tasks/multiplication/` со скелетом + тестами + workflow `.forgejo/workflows/grade.yml`.
5. Пушит ветку `submits/multiplication` (на ней — тот же скелет, что в `main`).
6. Создаёт задание `task_name=multiplication`, `allowed_files_glob=tasks/multiplication/multiplication.cpp`.
7. Жмёт **Distribute** — ветка раздаётся всем форкам, статусы становятся `pending`.

Дальше — **студент**:
1. В `/edu/student/assignments` видит задание `pending`. Открывает свой fork, чекаутит ветку `submits/multiplication`.
2. Пишет реализацию в `tasks/multiplication/multiplication.cpp`, коммитит, пушит.
3. CI запускается. Статус → `running` → `done` (или `failed`). PR создаётся автоматически.

Дальше — **TA**:
1. Открывает `/edu/teacher/assignments/<id>/submissions/<subID>`.
2. Просматривает diff, оставляет комментарий-замечание.
3. Студент исправляет, пушит снова. Auto-grade обновляется.
4. TA нажимает **Approve** (фиксирует оценку), потом **Merge**. Статус → `merged`.

### Сценарий: Обновление условий задания

```
Преподаватель:
  1. Обновляет репозиторий-шаблон (меняет тесты/условия).
  2. На странице submissions нажимает "Sync All Forks".
  3. Изменения попадают во все студенческие форки.
```

### Сценарий: Массовый импорт студентов

```
Преподаватель:
  1. Готовит CSV-файл: ФИО, email (опционально), группа (опционально).
  2. На странице курса: Import from CSV → загружает файл.
  3. Проверяет preview: корректирует логины/email при необходимости.
  4. Нажимает "Import All".
  5. Скачивает CSV с логинами и паролями → передаёт студентам.
```

## Цветовая схема статусов

| Статус | Цвет | Значение |
|--------|------|----------|
| `started` | Серый | Студент начал задание (форк создан) |
| `submitted` | Синий | Студент отправил решение (push) |
| `passed` | Зелёный | CI/CD тесты пройдены |
| `failed` | Красный | CI/CD тесты не пройдены |
| `graded` | Фиолетовый | Преподаватель выставил оценку |
